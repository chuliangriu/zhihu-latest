[**点击体验《未见之人》静态 Demo**](https://agent-6aa88293a994--effervescent-biscotti-3380a8.netlify.app/)

进入 Demo 后，你可以选择 **Noah** 或 **Iris** 两个预设身份，从他们各自与 AI 刘看山的一次正常对话开始，沿故事线体验**发现相关表达、理解关联、确认纸条，再决定是否走近**的完整过程：

- **Noah：私域连接私域**——让两段经用户授权的私人表达相遇。
- **Iris：私域连接公域**——让私人对话中的问题，与知乎已有的公开表达相遇。

> ***它展示的不是 AI 如何再给一个答案，而是一句话如何在用户授权后，找到可能与它有关的人。***

## 一、产品概述

我们越来越习惯把没想明白、也未必愿意公开的问题交给 AI：

> *一本几乎没人看的小说，还要不要继续？*  
> *明明有一间客厅，家人为什么越来越少坐在一起？*

AI 给出了回答，这些话却常常停在私人窗口里。那个也在想同一件事的人，不知道你的存在；你也看不见他。

**《未见之人》由此设想了一个“看山们的信箱”**：让私域中经用户授权的表达进入共同可见层，也让散落在知乎公域、因话题、时间和热度彼此错过的话，重新来到彼此面前。

在这里，每个人仍只与自己的 AI 刘看山对话。只有当用户愿意，才会有一句经本人预览、修改和确认的话被折成纸条，投入信箱。此后 **7 天**，除非主动撤回，这张纸会停留在***“此时此刻”***，等待真正相关的人出现。

> ***答案和“有答案的人”并不稀缺。***  
> ***真正难找到的是：此时此刻，还有谁停在与我相近的位置？***

因此，看山会让用户看见两种人：

- **处境相近的人：** 对方未必已经解决问题，却能带来***“原来不只我”***的确认。
- **处境不同、冲突相关的人：** 例如一个等待小说被看见，一个等待工作付出得到反馈。对方不能提供标准答案，却可能带来未曾考虑的视角，避免“只与相似者相遇”形成另一种信息茧房。

这种“不同”不是随机跨界，也不是为了制造惊喜而牵强联想。AI 必须用双方真实表达说明具体关联，同时保留差异。

> **相近处境让人感到自己并不孤单；**  
> ***相关差异则让交流带来新的视角。***

当关联出现，看山会把那句话带到用户面前，并说明它为什么与此刻有关。看见之后，它便退后一步：用户可以停下，也可以亲自回应；对方可以回应，也可以保持沉默。至于两个人会不会走近，不由 AI 安排。

## 二、创作思路：在社交中，AI 应该代理什么？

AI 社交产品正在代理越来越多的环节：理解用户、筛选对象、判断契合度、生成开场白，甚至让 AI 分身提前交流。这些能力提高了效率，也让我们想问：如果一切都被预测和安排，一段关系里还有什么需要由两个人亲自发生？

> ***《未见之人》希望重新划定一条边界：AI 代理发现，人保留选择。***

- **AI 代理发现**  
  理解表达，在难以被搜索或推荐的内容之间发现关联，并说明依据。
- **人保留选择**  
  是否走近、说什么、是否回应，都由真实的人决定。

我们不把***差异、等待和不确定***视为应该消除的摩擦。对方不是一份画像计算出的“完美匹配”，而是拥有自身经历和意愿的真实他者。

我们之所以期待被看见、理解或见证，正因为回应来自另一个人的自主选择：它可以发生，也可以不发生。

## 三、核心机制：看山们的信箱

“看山们的信箱”把私密、授权和发现的边界变成一个可理解的产品机制：

> *每个和刘看山聊天的人，都有一个只听见自己的看山。*
>
> *看山们不交换完整对话。只有当用户愿意把其中一句话折成纸条，它才会进入共用的信箱。*
>
> *另一个看山遇见真正相关的人时，才会把这张纸带给自己的用户。*

> ***信箱共享的是用户确认过的纸条，而不是聊天记录。***

它遵循三条边界：

- **私密边界：** 完整对话始终留在用户与自己的看山之间。
- **授权边界：** 纸条只包含用户同意呈现的表达和有限背景，并且可以随时撤回。
- **来源边界：** 对于知乎已有的公开内容，看山保留原问题、回答或评论的出处与语境，不把作者的话改写成 AI 的结论。

### 从一次 AI 对话到一次真实相遇

1. **AI 先正常回答**

   用户从知乎的 AI／刘看山入口提出问题，AI 首先完成这次问答，不为了引向社交而故意留下一个糟糕答案。
2. **在自然停顿处提出发现**

   当用户说出了与自己有关的具体处境，并且系统确实找到有依据的关联时，看山才邀请用户***“看看其他人”***。事实查询、信息不足或没有可靠候选时，不强行触发。
3. **呈现两种相遇方向**

   第一位与用户的现实处境更接近；第二位可能来自不同身份或话题，却面对相似的冲突。两条路径都必须有双方原话作为证据，并说明一处真实差异；没有足够依据时宁可少展示，也不为了凑数制造关联。
4. **先看表达，再看画像**

   页面先展示对方说过的一句话、时间与来源，再解释为什么把两段话放在一起。候选来自两类内容：用户主动授权的信箱纸条，或知乎公开的问题、回答、文章和评论。公开内容始终保留原文入口。
5. **用户决定停下还是回应**

   看见本身就是一次完整结果。用户可以返回原对话，也可以选择一位继续走近；产品不展示匹配分数，也不保证对方理解、认同或回复。
6. **回应之前，用户先确认自己的纸条**

   看山根据刚才的对话整理一张草稿，用户可以预览、修改，再决定是否投入信箱。纸条未来 **7 天**可被相关的人发现，且能随时撤回；未经确认的完整对话不会进入信箱。
7. **按来源走向不同的后续**

   如果对方来自授权私域，纸条可在一次确认后投入信箱并递给当前对象，后续的话仍由用户自己写；如果对方来自知乎公域，用户的纸条只进入自己的信箱，不自动递给原作者，也不自动发布评论，用户可以回到原文亲自回应。
8. **把关系交还给知乎**

   当前 MVP 在用户选择继续后，跳转到已核实的知乎个人主页或原文入口，实际私信与评论由用户在知乎完成。完整产品中，用户还可另行确认把纸条公开到知乎圈子；圈子承载公开纸条并提供“进入看山们的信箱”的入口，让新的表达继续被阅读、回应和发现。

```text
私域提问 → AI 正常回答 → 看见两种相关表达 → 用户选择
                                      ├─ 授权私域：确认纸条 → 投入信箱并递给 TA → 去知乎继续交流
                                      └─ 知乎公域：确认本人纸条 → 投入信箱 → 回到原讨论回应

另行确认公开 → 纸条进入知乎圈子 → 读者进入看山们的信箱／看山按关联主动递送
```

## 四、为什么是知乎

知乎的价值不只是内容多，而是每段表达都连着具体的人、原始语境和仍可继续的讨论。对《未见之人》来说，这些内容不是供 AI 摘要的语料；它们的出处、作者和回应入口，本身就是产品的一部分。

### 1. 让散落在公域里的表达重新进入讨论

在 Iris 的 Demo 改编场景中，她在私域里谈的是：家人为什么会在客厅短暂停留。看山却在一篇讨论“怎样让读者愿意继续读下去”的知乎文章下，发现了一条 3 天前、赞同和回复都为 0 的评论。两段话没有相同关键词，却都在追问：怎样让人自愿留下。

产品不会把这条评论改写成 AI 的答案，而是保留文章主题、评论原文、时间和互动状态，再让 Iris 自己决定是否回到原讨论回应。这样，一条被热度排序埋下去的表达，因为与另一个人的此刻有关，重新回到了知乎的阅读与讨论中。

### 2. 让经授权的私域表达被另一个人看见

在 Noah 的 Demo 中，他在与看山的私域对话中谈到，自己写了很久的小说几乎无人阅读。只有在他预览并确认后，这段话才会成为纸条进入“看山们的信箱”。当 Mika 出现时，看山发现：一个等待作品被看见，一个等待工作付出得到反馈；两人的生活不同，却都因缺少回声而失去了判断下一步的尺度。

Noah 可以把纸条投入信箱并递给 Mika，再决定是否继续交流。完整聊天不会被共享，后续的话也仍由 Noah 自己写。这里离开 AI 私域的不是整段对话，而是用户明确授权的表达，以及由此产生的一次真人连接。

### 3. 让纸条通过知乎圈子继续生长

在完整产品中，用户还可以另行确认，把纸条公开到知乎圈子。圈子承载公开纸条，并提供“进入看山们的信箱”的入口；用户可以从圈子浏览这些表达，也可以进入信箱查看卡片。公开后的纸条允许所有人阅读，但看山只会在具体关联成立时，主动把它递给相关的人。

因此，“公开可浏览”和“由看山定向发现”是两层机制：前者让表达进入知乎公共讨论，后者让它抵达原本可能错过的人。新的回应又会成为知乎里的真实内容，被阅读、讨论，并在未来与新的处境发生关联。

这延续了知乎“人生成内容，内容连接人”的社区逻辑：AI 不把真人表达压缩成无来源的答案，而是让人回到原文、回到作者，也让原本停在私域里的话在授权后重新进入社区。

## 五、技术方案

当前 MVP 采用前后端分离架构。前端以原生 HTML、CSS 和 JavaScript 实现完整交互，通过同域接口访问服务端；后端基于 Node.js 22、TypeScript 与 Express 5，使用 Zod 校验请求和模型输出，以 OpenAPI 约束接口合同。会话、纸条、授权和发现记录由 Supabase 持久化，Redis 用于限流、预算和多实例状态，模型调用兼容 OpenAI 接口。模型与知乎平台的密钥只保留在服务端，不进入浏览器。

### 1. 对话与发现触发

用户进入产品后，`POST /api/chat/reply` 以 SSE 流式返回刘看山的正常回答。系统同时判断这段对话是否已经形成一个具体、可被他人理解的处境，但不会为了启动社交而打断回答。只有在自然停顿处、且确实找到可靠候选时，前端才出现“想要看看其他人吗”；事实查询、表达不足或证据不够时，系统可以直接返回 `no_match`。

### 2. 关联发现与可解释输出

发现流程不是让模型凭空“推荐一个人”，而是分为候选召回、关联分析、程序校验和展示文案四步：

1. 从经授权的信箱纸条与可用的知乎公开内容中召回候选；
2. 模型分析双方表达的共同处境、关键差异和关联理由；
3. 服务端回查双方原话、来源、时间、授权状态与安全条件；
4. 仅把通过校验的证据交给模型组织成用户可读的说明。

系统保留两条发现路径：`situationClose` 寻找现实处境更接近的人，提供“原来不只我”的确认；`structureRelated` 寻找背景不同但冲突结构相关的人，引入新的理解角度。第二条路径不是随机跨话题，也不是按“惊喜度”匹配，而必须同时指出一处真实共同点与一处真实差异。模型只负责理解和表述，不能决定授权、人数、时间、界面状态，也不能生成“已发送”“已读”等事实。

### 3. 私域与公域候选来源

私域候选池只读取用户已经确认、尚未撤回、仍在 7 天有效期内、非本人且未被删除的纸条；草稿永远不会进入召回。系统会随信箱规模在 `scarce`、`growing`、`mature` 三种策略间调整召回范围，但不会因为候选少而降低授权、证据或安全标准。冷启动演示使用明确标注“非真人”的合成卡片，只用于验证交互，不能形成真实收件记录。

公域侧已经实现知乎官方搜索适配，可保留内容类型、作者、摘要、原文链接和互动信息，并为后续交流提供可回溯的原始语境。由于当前搜索结果只能稳定取得编辑时间，不能据此证明首次发布时间，MVP 不会把 `EditTime` 冒充 `PublishedAt`，依赖“近期发布”的公域真人召回暂时保持关闭。经 OAuth 授权后，系统也只最小读取当前用户近期创作与收藏，用于补充有限背景，而不是建立完整用户画像。

### 4. 纸条授权与生命周期

纸条先以草稿生成，用户可以预览、修改和确认；编辑接口使用版本号，避免旧页面覆盖新内容。只有确认后的纸条才进入 7 天可发现状态，用户撤回后立即停止新的匹配与递送。若对方来自授权私域，“确认入箱”和“递给当前对象”由同一数据库事务完成；若对方来自知乎公域，系统只保存用户自己的纸条，不替用户把内容发给原作者，也不自动发布评论。

后端数据结构分别记录会话、消息、主题展示、发现快照、纸条版本、授权与递送状态，使“说过什么”“允许公开什么”“看见了谁”彼此分离，也方便之后审计和撤回。

### 5. 把交流交还给知乎

当用户决定继续走近，`POST /api/handoffs` 只返回经过白名单校验的知乎原文或个人主页入口，不接收、代写或传输用户准备发送的私信和评论。真实的话仍由用户自己组织，并在知乎亲自发送。圈子公开则是完整产品中的下一层回流机制：用户再次确认后，纸条才可进入圈子；当前 MVP 尚未把这一步接入真实发布接口。

### 6. 安全、成本与工程验证

服务端将浏览器 Session 与内部身份分离，并使用内部 Token、短时 HMAC、请求与响应大小限制、账号与 IP 限流、并发和 Token 预算、幂等键及动态模型熔断控制风险与成本。模型输出经过 Schema 校验、Prompt Injection 检查、来源回查和 URL 白名单验证，监控信息也会脱敏。当前代码已通过后端 122 项、前端 43 项自动化测试，覆盖主要接口、授权状态、候选规则和交互流程。

## 六、知乎能力与现实边界

当前代码已经完成知乎官方搜索结果的结构化适配、授权用户近期创作与收藏的最小读取接口，以及跳回知乎原文或个人主页的安全交接；这些能力足以验证“发现关联—解释依据—由用户回到知乎继续交流”的核心链路。

但当前 MVP 仍是机制验证：真实私信、评论和圈子发布尚未接通，公域结果也因缺少可核验的首次发布时间而暂不进入“近期真人”匹配；演示中的合成卡片不代表真实用户。正式上线前，还需要完成 OAuth 状态校验、令牌刷新与解绑协议，并在生产环境验收 Supabase、Redis、部署平台和跨账号递送。产品不会把这些待接能力描述成已经发生的真实互动。

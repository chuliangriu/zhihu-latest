# 《未见之人》未完成事项

本文用于同事接手后理解剩余工作，仅保留尚未落实或未验证通过的事项。

- **已确定·待落实**：产品方向已经确认，接下来按本文实现或完成联调；不需要重新讨论是否采用。
- **待检查**：已有代码或接入基础，需要检查实际配置与运行结果，才能判断是否可用。
- **待确认**：方案尚未确定，应先讨论，不能自行当作已确定要求实现。

## 1. 知乎登录与用户背景

| 项目 | 状态 | 剩余事项与解释 |
| --- | --- | --- |
| app_id / app_key | 待检查 | 这是应用接入知乎 OAuth 登录所需的凭证。目前只确认线上能打开识别“未见之人”的知乎授权页，尚未验证用户确认后是否成功返回、换取令牌并建立本站登录状态。需要完整走一次授权登录。 |
| Access Secret | 待检查 | 这是服务端调用知乎开放平台的凭证，用于公开搜索、用户数据等接口，与登录应用的 app_key 不同。仓库已有调用代码，但尚未确认 Vercel 当前配置是否有效，以及接口是否实际返回可用数据。 |
| 用户 OAuth access_token | 待检查 | 这是每位用户授权后取得的令牌，用于代表该用户读取获准数据。需要验证是否正确获取、保存和使用，并检查过期、退出及不同账号之间的隔离；不能仅凭授权页可达就视为已完成。 |
| 有限背景 | 已确定·待落实 | 接通授权后的近期创作与收藏读取，再让模型整理成有限背景。当前代码尝试读取近 90 天内容，每类最多 8 条；这是已有逻辑，不代表线上已成功接通。需要将数据读取、模型整理与页面呈现连起来，资料不足时保留手动补充方式。 |
| 直答个人知识库 | 待确认 | 个人知识库与创作、收藏不是同一类数据。需要先确认本轮是否需要读取；若需要，再确认官方是否支持通过多用户授权读取各自的知识库，不能默认登录成功后即可获得。 |

背景读取依赖登录授权、Access Secret、有效的用户令牌、数据库和模型服务共同工作。检查时应分别定位：未接通、权限或令牌有问题，还是该用户本身没有足够资料。

## 2. 候选来源与冷启动

本轮冷启动的目标是让评委能输入自己的内容，看到真实模型如何理解、匹配并呈现相关表达。候选可以提前准备，不要求每次都从实时搜索开始。

- **已确定·待落实｜统一卡片格式。**  
  真人纸条与知乎公开内容尽量沿用同一套纸条卡片结构和视觉形式，不分别做成两种明显不同的内容样式。知乎公开内容在右下角以小字注明“来自知乎公开表达”，附原文链接即可。

- **已确定·待落实｜取消随机 50% 分流。**  
  当前逻辑在没有相关真人纸条时，会随机决定先尝试公开内容还是虚构样本。调整为：先尝试相关真人授权纸条，再尝试预存知乎公开纸条；仍没有可靠匹配时，再实时搜索知乎并重新做关联分析。这里的“未匹配上”也包括库存中有内容、但模型没有找到足够关联的情况，不能只在库存完全为空时才搜索。最终仍没有可靠结果，就不推荐。

- **已确定·待落实｜提前准备公开库存。**  
  提前捕捉一部分知乎公开内容，整理成可被匹配和展示的纸条卡片。库存是实际运行时的候选来源，不是固定给某段用户输入播放的预设结果；新的输入仍由模型动态判断与哪些纸条有关。

- **已确定·待落实｜虚构人物单独演示。**  
  虚构人物与预设故事保留在独立演示体验中。正常的自由体验按“真人纸条—公开库存—实时搜索”的顺序运行，不再随机混入虚构人物。

- **待检查｜找回已有公开材料。**  
  前序检查曾在队友代码包中发现 100 条公开材料，但当前仓库的公开内容文件记录为 0 条。需要核对那批材料，确认可用内容并导入实际候选库存；本项是恢复数据，不是重新选择代码仓库。

- **待检查｜实时搜索。**  
  已有知乎搜索适配代码，但尚未验证真实凭证、接口返回与完整调用链。需要检查“库存未找到可靠匹配—发起搜索—返回内容—重新匹配—展示卡片”能否走通。

- **待确认｜时间展示。**  
  部分公开内容只能取得编辑时间，无法证明首次发布时间。需要确认这些内容在纸条上如何显示时间，以及历史库存如何与产品“此时此刻”的定位衔接。此项尚未确定具体处理规则。

## 3. 留信与本帖回复

- **已确定·待落实｜无匹配也能留信。**  
  用户聊完后，即使没有出现相关候选，也能主动把刚才的表达整理成纸条，编辑后确认保存。后端已有“只入箱”的能力基础，但当前前端留信主要跟在候选展示之后，需要将入口独立出来，让本次没有找到人的表达也能留下。

- **已确定·待落实｜明确留信范围。**  
  留信时让用户明确选择：是否允许被匹配、显示什么身份、是否接受联系及保留多久。目前后端有相关字段，但前端确认请求直接提交昵称、允许联系和 7 天；需要把这些设置变成用户能理解并作出选择的操作。

- **已确定·待落实｜先看关联，再决定交流。**  
  出现候选时，先展示对方表达及关联理由，让用户了解为什么把两段话放在一起。用户看完后自行选择是否回应，不能把“出现匹配”直接当作用户已经决定交流。

- **已确定·待落实｜回复留在站内当前帖子。**  
  用户点开纸条后，可以在该纸条对应的站内帖子／讨论页面阅读并回复，回复需要实际保存并能在本帖看到。原文链接保留作来源入口，但本轮回复发生在本站。交流范围收敛为本帖回复，不继续扩展此前讨论的多轮递信、独立收件箱和到信通知流程。

- **待检查｜纸条管理。**  
  已有纸条保存、有效期与撤回相关实现，需要验证刷新页面、退出后重新登录时，是否仍能查看和撤回自己的纸条，并检查到期后的状态。不能只验证当前页面刚保存时的临时列表。

## 4. 模型与运行条件

- **待确认｜模型服务。**  
  还未确定最终使用的供应商、模型与费用范围。现有代码兼容 OpenAI 风格接口，但旧配置中的地址和模型名称不等于已确认的最终选择。

- **待检查｜模型 API Key。**  
  仓库已有真实模型调用代码，也保留 Mock 模式。需要确认 Vercel 配置中有可用的模型凭证，并以真实调用分别验证自由聊天、关联分析、背景整理与纸条生成；不能用固定输出的演示结果代替连接检查。

- **待检查｜数据与状态。**  
  验证 Supabase、Redis 和正式登录状态是否连接正常。重点检查纸条和回复是否实际保存、不同账号数据是否隔离，以及刷新、重新登录或服务重启后是否仍可恢复。当前本地临时身份和内存存储不能证明正式环境已可用。

- **待落实｜缺失模块。**  
  当前仓库业务代码引用了三个缺失的 guard 模块：discovery-trigger 负责发现触发判断，conversation 负责对话预检查，matches 负责关联与证据校验。需要补齐这些模块，以及必要的配置、登录和部署文件，再跑通构建；不能绕过这些判断只让页面显示结果。

## 5. 已知问题

- **待检查／修复｜匹配过早、单候选仍显示“选择二”。**  
  前序记录中出现过用户尚未充分表达就触发匹配，以及实际只有一个候选却仍显示第二项的情况。需要复核现有版本，调整触发时机，并使展示数量与真实通过校验的候选数量一致。

- **待检查／修复｜两人同时使用时“请求频繁”。**  
  该问题有历史记录，但根因尚未确认。需要用两个账号同时体验，判断错误来自本站限流、并发或预算，还是模型／知乎上游的限制，再针对原因处理。

- **待落实｜修正测试写死日期的问题。**  
  历史测试把纸条有效期固定在 2026-09-22，后来运行时被正确判为过期。需要调整测试时间的设置，使其能稳定验证有效、过期等状态，而不是取消业务本身的过期判断。

- **待检查｜真实链路。**  
  完成以上接入和修改后，用真实模型、真实存储和两个账号验证匹配、无匹配留信、本帖回复、过期及撤回。现有历史测试结果不等于当前版本已通过联调；验证后再核对 README 中的完成度描述。
